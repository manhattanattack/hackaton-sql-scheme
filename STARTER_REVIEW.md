# Разбор STARTER_DB_CHANGES.md

Правки сравнивались с версией репозитория 6d46c02. Они написаны к более раннему варианту, но требования к Identity принимаются как текущие. По уточнению владельца БД ещё нет: сценарии переноса/обновления удалены, проектируем итоговую схему.

| Пункт | Конфликт с прежней версией | Решение |
|---|---|---|
| A: учётные данные принадлежат Identity | Были собственные users/auth_sessions | Удалены из проектируемой схемы. Identity-таблицы/роли создаёт backend EF/UserManager, без ручного PasswordHash/SecurityStamp |
| A: email уникален | Был свой lowercase-email контракт | Нормализация теперь Identity; требование уникального полного NormalizedEmail и case-insensitive collation проверяет начальное подключение FK |
| B: сохранить числовой профиль | Уже user_profiles.id BIGINT | Сохранён, как и user_id во всех бизнес-таблицах |
| B: auth_subject хранит Identity Id | Раньше ссылался на собственную users | Теперь итоговый FK на AspNetUsers.Id; ожидаются VARCHAR(191), utf8mb4_bin с обеих сторон |
| B: RESTRICT при удалении аккаунта | Был CASCADE | Установлен RESTRICT. Очистка бизнес-данных перед удалением — отдельный сценарий backend |
| B: повторный профиль | UNIQUE уже был | QA02 идемпотентен, проверен на параллельных вызовах |
| C: demo seed через UserManager | SQL создавал технические аккаунты | 03_seed только каталог; QA02/07_demo_profile_seed используют существующий реальный аккаунт |
| Доступ/роли | SQL мог восприниматься как полная авторизация | Зафиксирована ответственность backend: проверенный principal, User/Admin, защита каталога и персональных функций |
| AI отдельно | История промптов находилась в общей схеме | Вынесена в 08_prompt_schema.sql с отдельными запросами и JSON-контрактом. Кеш упрощений не добавлялся |
| Перенос старой БД | Был каталог migrations | Удалён по уточнению владельца; вместо переноса только порядок первичного создания |

## Что готово со стороны БД

- Схема бизнес-таблиц и отдельной истории промптов.
- Начальные проверки определений Identity/профиля, email-индекса и orphan-ссылок.
- FK с RESTRICT после создания Identity.
- Идемпотентное связывание аккаунта и профиля, области персональных SQL-запросов.
- Каталожный seed без аккаунтов, хешей и токенов; отдельный seed уже существующего профиля.
- Актуальные Mermaid/PNG/PDF/SVG и SQL-тесты.

## Что ещё проверяет backend

- Реальные EF-таблицы и совместимость версий EF/MySQL-провайдера.
- UserManager/RoleManager: регистрация, User по умолчанию, запрет самостоятельного Admin.
- Уникальность Test@Example.com/test@example.com при реальной регистрации.
- Вход, refresh, хранение токенов на MAUI и политики административных действий.
- Интеграционный запрет API-доступа пользователя A к персональным данным B.

Результаты DB-тестов и ограничения тестовой заглушки — в VERIFICATION.md. Код .NET не изменялся.

## Уточнение фокуса после согласования Identity

Владелец выбрал подбор постоянной работы по обычным условиям. Удалены таблицы личной доступности и обязательных часовых интервалов, часовой пояс профиля и Q11. График теперь поле вакансии schedule_type, формат — work_format, срок договора — contract_type. Рекомендации формируются по навыкам, опыту, зарплате и условиям, без проверки личного календаря. Идентификаторы профилей и контракт Identity сохраняются. Миграций нет, БД ещё проектируется.
