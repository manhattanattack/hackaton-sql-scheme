# Регистрация, один промпт и адаптеры источников

Это контракт БД для бэкенд-разработчика. В репозитории реализованы схема MySQL и SQL-запросы учётных записей, сессий, промптов, подбора и истории. Сервер, ИИ и загрузчики в этот репозиторий не входят.

## Регистрация и вход

Для MVP: email + пароль, один тип пользователя — соискатель. Готовы две таблицы: `users` с учётными данными и `auth_sessions` с серверными сессиями. Привязка профиля физическая: `user_profiles.auth_subject → users.id`, UNIQUE + FK. Строковый `users.id` (обычно UUID) и числовой `user_profiles.id` — разные идентификаторы.

SQL-операции находятся в `05_auth_queries.sql`:

| Шаг | SQL | Обязанность бэкенда |
|---|---|---|
| Регистрация | QA01 | Проверить email/пароль, нормализовать email, вычислить готовый хеш пароля, сгенерировать ID; создать учётную запись и профиль в одной транзакции |
| Поиск при входе | QA02 | Нормализовать email тем же способом; проверить введённый пароль своим password hasher по возвращённому хешу |
| Создание сессии | QA03 | После успешной проверки создать криптографически случайный токен, передать в SQL его SHA-256 и срок действия |
| Авторизация запроса | QA04 | Вычислить SHA-256 полученного токена; использовать возвращённый `profile_id` как владельца данных |
| Выход | QA05 / QA06 | Отозвать одну или все сессии, убрать токен на клиенте |
| Успешный вход | QA07 | Обновить время входа после создания сессии |

`normalized_email` — обрезанный по краям email в нижнем регистре; одинаковая нормализация обязательна при регистрации и входе. На поле установлен UNIQUE, а CHECK отклоняет верхний регистр/краевые пробелы. Синтаксис и допустимость email проверяет бэкенд.

Пароль хешируется и проверяется только в коде бэкенда с помощью подходящего password hasher с солью. `SHA256(password)` в этой схеме не используется. В SQL передаётся только готовый `password_hash`; результат QA02 никогда не возвращается клиенту.

Сессионный токен — отдельная случайная строка с энтропией не менее 256 бит, не производная от пароля. Клиент получает исходный токен из памяти бэкенда, БД получает только 64-символьную hex-запись его SHA-256. QA04 проверяет срок, отзыв и состояние учётной записи. Отдельный refresh-token протокол не реализован: для простого MVP достаточно сессии со сроком действия и повторного входа. Если команда выбирает другую схему токенов или Identity, её нужно отдельно согласовать с этими таблицами.

Все операции с профилем, навыками, избранным и историей получают `user_id` из QA04 на сервере. ID из запроса клиента не является основанием доступа. SQL-файлы выполняются серверным подключением; пользователи приложения не получают прямого доступа к MySQL.

Нормализация, проверка пароля, генерация токена и HTTP-маршруты остаются работой вашего бэкенд-разработчика. В этом репозитории реализована только поддержка этих действий со стороны БД. В демо-данных учётные записи заблокированы и не имеют рабочих паролей.

## Один большой промпт вместо анкеты

Пользователь пишет, например: «Учусь, знаю C# и SQL, опыта нет. Могу работать по будням с 16 до 22 по московскому времени, хочу удалённую подработку от 25 тысяч рублей в месяц».

Бэкенд передаёт текст ИИ и получает структурированные поля: навыки, доступные интервалы, место, формат работы, желаемую оплату, опыт. Затем валидирует результат, сопоставляет навыки с `skills`, сохраняет подтверждённые данные профиля и вызывает Q03 из `02_queries.sql`. Если критичная часть текста неоднозначна, приложение уточняет её; неизвестные значения не следует выдавать за извлечённые факты.

Теперь исходный текст сохраняется в `search_requests.prompt_text` (QP01), а результат разбора — в `parsed_filters` (QP02). Ошибка сохраняется QP03; состояния: `pending → parsed` или `pending → failed`. Формат JSON задан в `JSON_CONTRACT.md`. В `search_results` сохраняются найденные объявления и объяснения, поэтому история показывает результат конкретного запроса.

Q03 поддерживает `@is_remote` для строгого выбора формата работы и `@experience_months` для ограничения требуемого стажа. `@include_remote` отдельно управляет добавлением удалённых вакансий к географической выдаче. По одному тексту эти значения сначала извлекает и валидирует бэкенд, затем передаёт в SQL.

После разбора бэкенд начинает короткую транзакцию, блокирует строку профиля `SELECT id FROM user_profiles WHERE id=@user_id FOR UPDATE`, обновляет навыки и доступность из текущего промпта, выполняет Q03, блокирует принадлежащую пользователю строку `search_requests` через `FOR UPDATE`, очищает старый снимок QP06 и записывает результаты QP07. Затем фиксирует транзакцию. Вызов ИИ выполняется **до** этой транзакции. Одинаковый порядок блокировок нужен для всех параллельных подборов одного пользователя. Внутренние START/COMMIT из Q10/Q11 в этом сценарии нужно заменить управлением общей транзакцией драйвером; вложенные транзакции MySQL не поддерживает.

QP04/QP05 возвращают мои запросы, QP08 — сохранённую подборку. Чужие запросы не доступны через эти операции. Повторный запуск из истории требует повторного применения сохранённого JSON к параметрам/навыкам; простое чтение истории не запускает ИИ и не меняет профиль.

ИИ получает найденные записи из БД и объясняет совпадения. Идентификаторы вакансий и ссылки в ответе должны принадлежать результатам запроса. Возможность внешнего перехода сохраняется; работодатель получает заявку уже на исходном сайте.

## Разные API совместимы через адаптеры

Для каждого сайта пишется свой адаптер. Он получает ответ API/страницы и возвращает общий объект. Затем единый импортёр валидирует этот объект и сохраняет в MySQL.

```text
TrudvsemAdapter ──────────────────┐
Адаптер второго доступного сайта ─┼→ NormalizedVacancy → проверка → Q01 / Q02 → MySQL
Другой адаптер ──────────────────┘
```

Пример различий форматов: в спецификации HH заголовок называется `name`, на «Работе России» — `job-name`. Адаптер каждого доступного источника записывает название в `title`; код сохранения после этого одинаковый. HH сейчас исключён из плана MVP, поскольку доступ команды к его поиску не подтверждён. Этот пример не означает, что источник уже доступен для импорта.

Общий контракт адаптера, концептуальный C# интерфейс:

```csharp
public interface IVacancySourceAdapter
{
    string SourceCode { get; }
    IAsyncEnumerable<NormalizedVacancy> FetchAsync(CancellationToken cancellationToken);
}
```

`NormalizedVacancy` — DTO команды, его поля соответствуют параметрам Q02. Минимально обязательны:

| Поле | Значение |
|---|---|
| `SourceCode` | Зарегистрированный код из `sources.code` |
| `ExternalId` | Стабильный ID в рамках этого источника |
| `Title`, `Description` | Заголовок и полное описание; не подменять полную карточку сниппетом поиска |
| `OriginalUrl` | Проверенная HTTPS-ссылка на оригинальное объявление на домене источника |

Дополнительные поля: идентификатор и название работодателя, обязанности, требования, адрес/регион/город, оплата с валютой и периодом, график, навыки, статус и даты. Все сведения заполняются по исходным данным и правилам нормализации из `SOURCES.md`. Отсутствие зарплаты не означает нулевую зарплату, неизвестный график остаётся неизвестным. Сырой ответ при необходимости сохраняется в `raw_payload`, без секретов и ненужных контактных данных.

Адаптер HH использует `id` вакансии как `ExternalId`; адаптер «Работы России» — `companycode + ':' + id`. Внутренние числовые PK назначает MySQL. Одинаковый внешний ID разных сайтов допустим: уникальна пара `source_id + external_id`.

Последовательность сохранения:

1. По `SourceCode` определить внутренний `source_id`.
2. Нормализовать полный объект в коде загрузчика, до SQL. Преобразовать даты в UTC, валюту в согласованный код, навыки в справочник; неизвестное оставить неизвестным.
3. В одной транзакции выполнить Q01 для компании (если известна), Q02 для вакансии, заменить связи навыков и точные интервалы при наличии полного снимка.
4. Подтвердить транзакцию. Успешное время опроса обновить отдельно после сохранения всех полученных данных.
5. Ошибки и ограничения одного источника обработать отдельно, чтобы продолжал работать каталог уже сохранённых вакансий.

Для API-источника достаточно разобрать JSON. HTML-парсер нужен только для сайта, где выбран такой способ получения данных. Способ извлечения — ответственность конкретного адаптера; схему БД при каждом подключении сайта менять не требуется, пока хватает общего набора полей.

## Порядок работы на хакатоне

1. Инженер БД запускает новую схему или миграцию старой, передаёт бэкендеру SQL авторизации, подбора и истории. Бэкендер подключает свои обработчики входа и регистрации к этим запросам.
2. Загрузчик реализует `TrudvsemAdapter`: API уже проверен, есть данные без ключа. Для первой демонстрации достаточно небольшой выборки.
3. Команда соединяет промпт → извлечение данных ИИ → Q03 → карточка → переход на исходный сайт. Согласует поддерживаемые фильтры и честно показывает неизвестные условия.
4. После работающей цепочки проверяет доступ ко второму сайту и добавляет его адаптер. HH в текущий план не входит; возвращаться к нему стоит только после получения доступа. Сохранение, подбор и экран карточки используют те же таблицы.

Архитектура допускает несколько источников с самого начала. Для первой законченной демонстрации реализуйте один адаптер.
