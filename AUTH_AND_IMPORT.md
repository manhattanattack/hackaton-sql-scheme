# Контракт БД: Identity, профиль, промпт и импорт

Реализована только часть БД. Учётные записи, пароли, вход, Bearer/refresh-токены и роли реализует backend через ASP.NET Core Identity + EF Core. Вручную создавать таблицы Identity нашим SQL не требуется. Существующей БД нет; проект ориентирован на первоначальное создание схемы.

## Что согласовать с бэкендером

- Одна MySQL БД, совместимые версии EF Core и MySQL-провайдера.
- Identity с ролями: AspNetUsers, AspNetRoles, AspNetUserRoles, AspNetUserClaims, AspNetUserLogins, AspNetUserTokens, AspNetRoleClaims и служебная таблица EF. Их создаёт EF, а аккаунты/роли — UserManager/RoleManager.
- `AspNetUsers.Id` и `user_profiles.auth_subject`: VARCHAR(191), CHARACTER SET utf8mb4, COLLATE utf8mb4_bin, NOT NULL, InnoDB. Наш столбец уже определён так; Id Identity настраивает backend.
- Включить уникальность email в Identity и явный уникальный индекс полного `AspNetUsers.NormalizedEmail` в EF-модели. Стандартного неуникального EmailIndex недостаточно. Нормализация принадлежит Identity, не SQL; для ограничения независимо от регистра нужен согласованный case-insensitive collation (например utf8mb4_0900_as_ci). Начальный скрипт FK проверяет наличие такого полного уникального индекса и case-insensitive collation.
- Начальные роли User/Admin. Самостоятельная регистрация получает только User; роль Admin не берётся из пользовательского ввода.
- Каталог и персональные функции требуют авторизации; регистрацию и вход пользователь вызывает без неё. Административные действия требуют политики Admin. MySQL не заменяет проверку principal/ролей на уровне API.

## Профиль после регистрации

В `05_auth_queries.sql` больше нет создания аккаунтов, проверки PasswordHash и собственных сессий:

| Операция | SQL | Вход |
|---|---|---|
| Найти мой профиль | QA01 | Строковый Id из проверенного Identity principal |
| Создать профиль при первом GET /api/me | QA02 | Тот же Id, проверенное отображаемое имя |
| Изменить мой профиль | QA03 | Тот же Id и допустимые поля профиля |

QA02 использует UNIQUE(auth_subject) и ON DUPLICATE KEY UPDATE без перезаписи существующих данных. Повторные/параллельные вызовы возвращают один числовой user_profiles.id. Если Identity-аккаунт не существует, профиль не создаётся и ID не возвращается. На этот ID бэкенд переводит principal перед выполнением Q03–Q10 и QP-операций. Клиент не назначает себе чужой user_id.

Базовая схема создаёт профиль без FK, поскольку таблиц Identity ещё нет. После создания Identity выполнить `identity/01_preflight.sql`, затем `identity/02_link_profile.sql`. FK с ON DELETE RESTRICT устанавливается только при совпадении определений, уникальном email-контракте и отсутствии orphan-профилей. На диаграмме показана итоговая связь после этого шага.

Демо-аккаунты создаёт backend UserManager; PasswordHash/SecurityStamp вручную в SQL не вставляются. Затем QA02 создаёт профиль, а `07_demo_profile_seed.sql` может добавить ему демонстрационные навыки и избранное. `03_seed.sql` содержит только каталог.

Собственной таблицы сессий или refresh-токенов нет. MAUI хранит токены Identity в SecureStorage. Встроенные Bearer-токены Identity не JWT; logout не гарантирует мгновенного серверного отзыва уже выданного токена. Пароли, токены и ключ ИИ не сохраняются в профиле, raw_payload или логах.

Удаление Identity-аккаунта с профилем запрещается FK. Обработку навыков, избранного, промптов и переходов выполняет отдельный сценарий backend перед удалением.

## Один большой промпт

Таблицы search_requests/search_results вынесены в отдельный `08_prompt_schema.sql`, а операции — в `06_prompt_queries.sql`. Это уже подготовленное расширение с контрактом `JSON_CONTRACT.md`; оно не создаёт ничего в Identity. Кеш vacancy_simplifications в объём этой задачи не добавлялся.

QP01 сохраняет текст и состояние pending. QP02 сохраняет проверенный JSON и состояние parsed, QP03 — безопасный код ошибки и failed. QP04/QP05 читают только мои запросы, QP08 — найденные вакансии и объяснения. Навыки из JSON сопоставляются с user_skills, условия постоянной работы передаются в Q03. Свободные часы пользователя не собираются. Чужой user_id из клиента не используется.

Для согласованного подбора бэкенд после получения/валидации ответа ИИ открывает короткую транзакцию: блокирует строку своего профиля FOR UPDATE, заменяет навыки, выполняет Q03, блокирует принадлежащую пользователю search_requests, заменяет снимок результатов через QP06/QP07 и фиксирует транзакцию. Вызов ИИ выполняется до транзакции. Встроенные START/COMMIT Q10 в этом общем сценарии заменяются управлением транзакцией драйвером, вложенные транзакции MySQL не используются.

Q03 поддерживает только документированные условия. Неизвестные график, формат или срок договора не считается подтверждённым совпадением. Повторный запуск из истории требует применить сохранённые условия; простое чтение истории не запускает ИИ и не меняет профиль.

## Разные API совместимы через адаптеры

Для каждого сайта пишется свой адаптер. Он получает ответ API/страницы и возвращает общий объект. Затем единый импортёр валидирует этот объект и сохраняет в MySQL.

```text
TrudvsemAdapter ──────────────────┐
Адаптер второго доступного сайта ─┼→ NormalizedVacancy → проверка → Q01 / Q02 → MySQL
Другой адаптер ──────────────────┘
```

Пример различий форматов: в спецификации HH заголовок называется `name`, на «Работе России» — `job-name`. Адаптер каждого доступного источника записывает название в `title`; код сохранения после этого одинаковый. HH сейчас исключён из плана MVP, поскольку доступ команды к его поиску не подтверждён. Этот пример не означает, что источник уже доступен для импорта.

Общий контракт адаптера, концептуальный C# интерфейс:

```csharp
public interface IVacancySourceAdapter
{
    string SourceCode { get; }
    IAsyncEnumerable<NormalizedVacancy> FetchAsync(CancellationToken cancellationToken);
}
```

`NormalizedVacancy` — DTO команды, его поля соответствуют параметрам Q02. Минимально обязательны:

| Поле | Значение |
|---|---|
| `SourceCode` | Зарегистрированный код из `sources.code` |
| `ExternalId` | Стабильный ID в рамках этого источника |
| `Title`, `Description` | Заголовок и полное описание; не подменять полную карточку сниппетом поиска |
| `OriginalUrl` | Проверенная HTTPS-ссылка на оригинальное объявление на домене источника |

Дополнительные поля: идентификатор и название работодателя, обязанности, требования, адрес/регион/город, оплата с валютой и периодом, график, навыки, статус и даты. Все сведения заполняются по исходным данным и правилам нормализации из `SOURCES.md`. Отсутствие зарплаты не означает нулевую зарплату, неизвестный график остаётся неизвестным. Сырой ответ при необходимости сохраняется в `raw_payload`, без секретов и ненужных контактных данных.

Адаптер HH использует `id` вакансии как `ExternalId`; адаптер «Работы России» — `companycode + ':' + id`. Внутренние числовые PK назначает MySQL. Одинаковый внешний ID разных сайтов допустим: уникальна пара `source_id + external_id`.

Последовательность сохранения:

1. По `SourceCode` определить внутренний `source_id`.
2. Нормализовать полный объект в коде загрузчика, до SQL. Преобразовать даты в UTC, валюту в согласованный код, навыки в справочник; неизвестное оставить неизвестным.
3. В одной транзакции выполнить Q01 для компании (если известна), Q02 для вакансии, заменить связи навыков при наличии полного снимка.
4. Подтвердить транзакцию. Успешное время опроса обновить отдельно после сохранения всех полученных данных.
5. Ошибки и ограничения одного источника обработать отдельно, чтобы продолжал работать каталог уже сохранённых вакансий.

Для API-источника достаточно разобрать JSON. HTML-парсер нужен только для сайта, где выбран такой способ получения данных. Способ извлечения — ответственность конкретного адаптера; схему БД при каждом подключении сайта менять не требуется, пока хватает общего набора полей.

## Порядок реализации командой

1. Инженер БД передаёт базовую схему и требования к Id/email. Backend создаёт Identity, роли и безопасный seed через стандартные сервисы.
2. Подключить FK с RESTRICT и QA01/QA02 к проверенному principal. Проверить регистрацию, вход, refresh и разграничение User/Admin в API.
3. Добавить отдельную схему истории промптов и связать разбор одного текста с Q03. Согласовать поддерживаемые поля JSON.
4. Реализовать первый адаптер «Работы России», затем добавлять другие сайты после проверки доступа к данным. HH не входит в текущий MVP.

## Границы проверки

SQL-тесты используют только минимальную тестовую заглушку AspNetUsers с Id/NormalizedEmail. Они проверяют FK, уникальность, конкурентное создание профиля и области запросов. Они не доказывают, что реальные EF-настройки, UserManager, роли и HTTP-авторизация вашего приложения уже работают. Эти пункты остаются приёмкой бэкенд-команды.
